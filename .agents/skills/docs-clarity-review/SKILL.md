# docs-clarity-review

评估 `docs/` 中规格文档的需求清晰程度。本仓库的核心模型是「docs 翻译为代码，data 作为程序数据」，因此一篇 docs 的清晰程度 = 它能否被直接翻译为实现。

## 评估维度（六问）

对每篇 `docs/**/*.md` 依次回答，每问需引用原文证据：

1. **输入输出可定义**：能否一句话说清「喂进什么、吐出什么」？字段与类型是否明确？
2. **规则可判定**：每条规则能否判断「当前是否命中」？有无正反例？
3. **有验收样本**：是否存在「输入 → 期望输出」对照对（golden samples）？
4. **数据契约明确**：引用的数据源、schema 是否真实存在且稳定（如编号轴、`data/` 目录结构）？
5. **术语一致**：关键概念是否含义稳定，能否映射到数据字段？
6. **非确定性已声明**：哪些判断归人、哪些归程序，是否写明（如「倾向性准则」「作者保留判断权」）？

## 可编程分级

| 级别 | 判定标准 |
|------|---------|
| L0 | 背景描述，无输入输出（疑似应归 `data/`） |
| L1 | 有原则，无示例 |
| L2 | 有输入输出对照例 |
| L3 | 可操作：清单＋参数＋验证步骤 |
| L4 | 可验收：golden 数据集＋输出 schema＋人机分工声明 |

## 工作流程

1. 枚举 `docs/` 全部 `.md` 文件
2. 逐篇通读，按六问逐项判定，引用原文行号或原文片段作证据
3. 按 L0-L4 分级，L0 视为分类错误候选，建议移入 `data/` 对应主题目录
4. 为 L2-L3 给出升到 L4 的最短路径，从三件套中找缺口：
   - 输入契约（吃什么文件、什么结构）
   - 输出 schema（字段化定义，落到 `data/knowl/`）
   - 验收样本（把文内前后对照例抽出存入 `data/`，作为回归测试集）
5. 输出报告（格式见下）

## 输出格式

```
| 文档 | 级别 | 判定依据 | 缺口 |
|------|------|---------|------|
```

每篇文档必须给出：级别、至少一条原文证据、至少一个具体缺口、一条升级动作。报告末尾汇总「最适合首先实现的篇目」（级别最高者）。

## Pitfalls

- 不把「写得优美、逻辑自洽」当「清晰」：清晰的标准是可翻译为实现，不是可读性
- 样本只有一两个时不轻易评 L4：标注泛化性风险，建议扩充 `data/` 样本后再升
- 「倾向性准则、非硬规则」类声明是加分项而非缺陷：它声明了人机分工，是 L4 的必要条件
- 六问中任何一问完全无法回答时，级别上限为 L1
- 评估只读不改：不要在评估过程中顺手改写 docs/，升级动作留给后续任务

## Verification

- 报告覆盖 `docs/` 全部篇目，无遗漏
- 每篇均有级别、证据、缺口、动作四要素
- L0 候选均已给出迁移建议及目标路径
