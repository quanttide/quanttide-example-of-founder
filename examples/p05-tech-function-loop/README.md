# p05 技术职能协作循环 — 实验方案

## 实验目的

验证"技术线写骨架 + 职能线填业务逻辑"的协作模式能否闭环，以及"故意留坑"能否有效观察开发者的判断力。

## 背景

日志 2026-05-28：做了一个实验，技术跟职能线配合，提前写好骨干代码，故意留一个状态命令给职能线设计，观察他们能做出什么。

## 实验假设

1. 骨架代码能明确定义扩展点，职能线无需理解全貌即可填充业务逻辑
2. "故意留坑"可以有效区分主动思考和被动执行型开发者
3. 协作循环的可观察性有助于持续改进协作策略

## 实验设计

> 可选项：PoC 阶段可用真人走查替代编码仿真环境，降低实现成本。
>
> **伦理说明**：本实验在 PoC 阶段使用模拟环境，参与者被告知实验目的。若将来应用于真实团队，需满足：
> 1. 参与者事先知晓评估目的（"我们在验证协作流程"而非隐瞒）
> 2. 埋坑类型和数量事先由技术负责人和职能负责人共同确认，非单方面设计
> 3. 评估结果仅用于流程改进，不用于个人绩效

### 阶段 1：骨架代码设计

设计一个状态命令模式的骨架，包含：

- 接口定义：`CommandHandler` / `CommandValidator`
- 基础实现：`BaseCommand` / `EventBus`
- 故意留坑处：
  - 坑 A：边界条件（空状态时的命令处理）
  - 坑 B：异常处理（命令执行失败的回滚）
  - 坑 C：权限检查（跨职能操作的鉴权）

### 阶段 2：模拟协作

参与者（模拟职能线开发者）拿到骨架后，需要实现一个具体的业务命令：

```
实现"转派任务"命令：
- 将任务从 A 转给 B
- 需要通知 A 和 B
- 记录转派日志
- 限制：已开始执行的任务不可转派
```

观察指标：

| 观察点 | 主动发现坑 | 提问后处理 | 未发现坑 |
|--------|-----------|-----------|---------|
| 坑 A：空状态 | ✅ 自行处理边界 | ✅ 提问后修复 | ❌ 代码报错 |
| 坑 B：异常回滚 | ✅ 添加 try-catch | ✅ 按照提示添加 | ❌ 无处理 |
| 坑 C：权限检查 | ✅ 自行添加鉴权 | ✅ 按设计实现 | ❌ 绕过鉴权 |

### 阶段 3：观察报告

生成协作报告：

- 开发者决策路径记录
- 各坑位的处理方式统计
- 协作效率指标（首次交付时间/缺陷率/返工次数）

## 评价标准

| 指标 | 合格线 | 优秀线 |
|------|--------|--------|
| 骨架代码可理解性 | 60% 开发者无需额外解释 | 80% |
| 坑位发现率 | 50% | 70% |
| 功能正确交付率 | 70% | 90% |
| 协作反馈可用性 | 可追溯 | 可量化决策 |

## 原型实现

协作仿真环境 + 观察面板，包含：

- 骨架代码编辑器（技术线视角）
- 业务逻辑填充区（职能线视角）
- 坑位预设和记录系统
- 决策路径可视化
- 协作报告生成器

## 实验记录

- 每次实验的骨架代码版本
- 参与者的填充代码
- 坑位发现情况和处理方式
- 协作效率数据
